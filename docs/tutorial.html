OpenELIS Review Tooling

Set up a review for a branch, PR, or ticket

Write a checklist once, put it in front of reviewers on a deployment you already have, and get structured feedback back as issues — no frontend build, no fork, no redeploy.

time ~15 min steps 5 you need a running deployment + a Grist login

01

Author the checklist

Do this first — reviewers need something to work through.

Checklists live in one shared Grist document. Each review is a set of rows tagged with an instance slug — that slug ties the checklist, the overlay, and each reviewer's saved answers together. Pick one per feature or ticket.

Sign in to Grist, open UAT Checklists, and add rows to two tables:

TableWhat you add
UAT_MetaOne row for the review: instance, title, intro, jira.
UAT_StepsOne row per step: instance, step_key, required, section, section_order, step_order, do, expect, route.
⚠️ A row with an empty step_key breaks the entire checklist — reviewers get an error for every step, not just that row. That is deliberate: silently dropping a step could let a report claim everything passed. Run the check in step 02 after every edit.

Connect the authoring MCP once, then just ask — “add a step to My Feature (OGC-1234) covering the new export screen”.

# Claude Code CLI
claude mcp add --transport http grist \
  https://grist.openelis-global.org/api/mcp \
  --header "Authorization: Bearer <grist-api-key>"

On claude.ai, add that same URL as a custom connector and sign in — no key to paste. There is a bundled uat-authoring skill that teaches an agent these rules, so it reads before writing and verifies after.

02

Check it's live

One request tells you what reviewers will actually get.

curl -sS -o /dev/null -w '%{http_code}\n' \
  https://grist.openelis-global.org/uat/my-feature.json
✓You should see 200. That means a reviewer's browser will load exactly this checklist.
ResponseMeaning
200Live. Edits in Grist appear here within ~30 seconds.
404No checklist for that slug — usually a typo, or rows not added yet.
502A row is malformed and the whole checklist is unusable. The body names the culprit, e.g. {"error":"step row 35 is missing step_key"} — fix that row and re-run.

Re-run this after every edit. Because a bad row takes down the whole checklist, this one request is the difference between reviewers working and reviewers stuck.

03

Put it in front of reviewers

One script tag on a deployment you already have.

Add this before </head> in the app's page template:

<script src="https://grist.openelis-global.org/oe-review-widget.js"
        data-instance="my-feature"
        data-label="My Feature (OGC-1234)"
        data-src="https://grist.openelis-global.org/uat/my-feature.json"></script>
✓Reload the app — a “Review” tab appears in the bottom-right. If it doesn't, check the browser console: a blocked script usually means a Content-Security-Policy on the host page.

Can't edit the app's templates? Inject it at the reverse proxy instead — one sub_filter line, no application change. Recipes for nginx, Apache and a bookmarklet are in integration/README.md.

04

Review

What the reviewer does — no account, no setup.

They open the site, click Review, and work the list: each step gets pass / fail / n-a and an optional note, plus freeform notes for anything the checklist didn't ask about. Answers persist in their browser, so they can stop and come back.

✓Nothing is transmitted anywhere. Answers stay in the reviewer's own browser until they choose to export — worth saying out loud when you send the link.

Tell reviewers that a Fail is the useful outcome. A checklist that only confirms what already works tells you nothing you didn't know.

05

Collect & triage

From reviewer feedback to drafted issues.

Download review report produces two files — a readable .md and a structured .json. The reviewer sends you the Markdown (or pastes it into Claude themselves) and asks for triage.

# paste the report, then:
Triage this UAT report into ranked issues under My Feature (OGC-1234).
Group by severity, map each FAIL to a concrete story or task,
and tell me what passed.

From the real amr review, an 8-step checklist produced one story (carry AST interpretation through to the patient report), one task (add the worklist to the sidenav), and seven confirmed-working steps — from a reviewer who wrote no issue text at all.

✓Iterate without redeploying. Edit rows in Grist and reviewers pick up the change within ~30 seconds. Send the same link again.

When something looks wrong

SymptomCause & fix
502 on the checklistA malformed row — the body names it. Usually a blank step_key.
404 on the checklistSlug typo. instance is free text, so a misspelling creates a separate empty checklist rather than an error.
Every step says “optional”required was never set. Grist writes false for untouched rows, so nothing can fail the review.
Edit isn't showing upCheck X-UAT-Cache on the response. STALE means you're seeing a cached copy because the read service is failing.
No Review tabScript blocked — check the console for a CSP error, or confirm the tag is actually in the served HTML.
