01

Author the checklist

Do this first — reviewers need something to work through.

Checklists live in one shared Grist document. Each review is a set of rows tagged with an instance slug — that slug is what ties the checklist, the widget, and each reviewer's saved answers together. Pick one per feature or ticket.

Sign in to Grist, open UAT Checklists, and add rows to two tables:

TableWhat you add
UAT_MetaOne row for the review: instance, title, intro, jira.
UAT_StepsOne row per step: instance, step_key, required, section, section_order, step_order, do, expect, route.

Reviewers see steps grouped by section, ordered by section_order then step_order. route is the page a reviewer should open for that step.

step_key is required — a short stable id, unique in the instance (AMR-001). It ties a reviewer's answer to the step, so never change it once reviewers have seen it; reorder rows freely instead. required marks a step that must pass for the review to count.

⚠️ A row with an empty step_key breaks the entire checklist, not just that row — reviewers get an error for every step. That's deliberate: a silently dropped step could let a report claim everything passed. Run the check in step 02 after every edit.

Connect the authoring MCP once, then just ask — “add a checklist for My Feature (OGC-1234) covering the new screens”.

# Claude Code CLI
claude mcp add --transport http grist \
  https://grist.openelis-global.org/api/mcp \
  --header "Authorization: Bearer <grist-api-key>"

On claude.ai, add https://grist.openelis-global.org/api/mcp as a custom connector and sign in — there's no key to paste.

What makes a step worth writing

A do the reviewer performs and an expect they judge it against. Write the check for the thing you're unsure about — a missing feature is a perfectly good step, because a reviewer marking it Fail is exactly the signal you wanted.

From the real microbiology review: “After entering AST results, check whether the S/I/R interpretation is carried onto the patient's report.” It came back Fail — and became the top priority for the next iteration.

02

Check it's live

One request confirms reviewers will see it.

curl https://grist.openelis-global.org/uat/my-feature.json

That is exactly what a reviewer's browser will fetch. You should get your checklist back as JSON. Three responses worth knowing:

ResponseMeaning
200Live. Edits in Grist appear here within ~30 seconds.
404No checklist for that slug — usually a typo, or rows not added yet.
502A row is malformed and the whole checklist is unusable. The body names the culprit, e.g. {"error":"step row 35 is missing step_key"} — fix that row and re-run this check.

Re-run this after every edit. Because a bad row takes down the whole checklist, this one request is the difference between reviewers working and reviewers stuck.

03

Put it in front of reviewers

Pick the row that matches what you control.

Add one tag to the page template, before </head>:

<script src="https://grist.openelis-global.org/oe-review-widget.js"
        data-instance="my-feature"
        data-label="My Feature (OGC-1234)"
        data-src="https://grist.openelis-global.org/uat/my-feature.json"></script>

Nothing is bundled or vendored — the widget and the checklist are both fetched from the review service, so checklist edits need no redeploy.

Can't touch the app, but you run the reverse proxy? Inject it there — the app is untouched. Add to the location block that serves HTML:

# inject the review overlay into HTML responses
proxy_set_header Accept-Encoding "";
sub_filter_once on;
sub_filter '</head>' '<script src="https://grist.openelis-global.org/oe-review-widget.js" data-instance="my-feature" data-label="My Feature (OGC-1234)" data-src="https://grist.openelis-global.org/uat/my-feature.json"></script></head>';

Then nginx -s reload. That's the whole integration.

Needs the sub_filter module — check with nginx -V 2>&1 | grep -o with-http_sub_module. It's in the stock nginx image and most distro builds. Apache equivalent (mod_substitute) is in the repo docs.

Stand up a demo stack for the branch under review, then the router injects the widget for you:

cp .env.example .env      # host, domains, branch to build
./deploy.sh configure     # docker + cert renewal (idempotent)
./deploy.sh deploy --yes  # build + bring up the stack (20-40 min)
# point DNS at the host, then:
./deploy.sh certs         # Let's Encrypt
./deploy.sh seed          # demo data to review against

Reviewing a different branch is a change to .env, not to code.

No deployment at all — reviewing a design or copy? The widget also runs standalone with the checklist embedded in a single HTML file.

04

Review

What your reviewer actually does. No account, no training.

A Review tab appears in the corner of every page. Opening it shows the checklist; each step gets Pass, Fail or N/A plus an optional note, and there's a freeform box for anything the checklist didn't ask about.

05

Collect & triage

Reviewer feedback becomes issues without anyone writing issue text.

Download review report produces two files: a readable Markdown summary and a structured JSON twin. The reviewer sends you the Markdown — or pastes it into Claude themselves and asks for triage.

# OpenELIS review report — My Feature (OGC-1234) - Instance: `my-feature` · Reviewer: Beth Dunbar ## Checklist - [PASS] Open the worklist and confirm the seeded case is listed. - [FAIL] Check the result reaches the patient report. - note: Saves fine, but never shows up on any report. **Summary:** 3 pass · 1 fail · 0 n/a · 0 untested (of 4)

Claude reads the marks and notes, groups failures by severity, and drafts issues under the ticket. A real 8-step review produced:

Story
Carry the AST interpretation through to the patient report.
Task
Add the microbiology worklist to the sidenav.
Confirmed working
Seven steps across sign-in, case handling and result entry.

Then iterate

Checklists are live. Add or reword steps in Grist (or ask an agent) and reviewers pick up the change in about 30 seconds — no redeploy, no re-integration. Send the same link again.
